# Файловый сервис PISMO

Вложения больше не возят в базу. Файл кладётся на диск сервера, а в
сообщении остаётся ссылка.

## Зачем

Раньше клиент дописывал LONGBLOB порциями через `CONCAT`. На каждую порцию
сервер перечитывал и переписывал **весь** накопленный блоб — работа росла
квадратом от размера файла. Прогресс был виден только по границам порций
(у тридцатимегабайтного видео первая порция — почти четыре мегабайта, и
полоса минутами стояла на нуле), видео нельзя было перемотать, а телефон
возил мегабайты по протоколу MySQL, который для этого не предназначен.

## Протокол

Тот же, что у tus и у черновика IETF «Resumable Uploads» — три запроса:

| Запрос | Зачем |
|---|---|
| `POST /files` | создать загрузку: `Upload-Length`, `Upload-Name` (base64), `Upload-Sha` → `Upload-Id` |
| `HEAD /files/<id>` | сколько байт уже принято → `Upload-Offset` |
| `PATCH /files/<id>` | дописать с `Upload-Offset`; когда дошло до конца → `File-Key` (sha256) |
| `GET /files/<sha>/<имя>` | отдать файл; понимает `Range`, поэтому видео перематывается |

**Докачка.** Оборвалась связь — клиент спрашивает `HEAD`, узнаёт принятое и
продолжает ровно с этого места. Потерянной оказывается не вся отправка, а
несколько килобайт.

**Дедупликация.** Файл хранится под своей sha256. Если клиент прислал `sha`
заранее и такой файл уже лежит, `POST` сразу отвечает «готово» — по сети не
уходит ни байта. То же видео второму собеседнику отправляется мгновенно.

**Отпечаток вместо имени.** Ссылка на файл — это его содержимое, поэтому
отдача помечена `immutable`: браузер и клиент кешируют её навсегда.

## Установка

```
bash install-files.sh
```

Скрипт кладёт `files.js` рядом с релеем, заводит службу `pismo-files`,
открывает порт 8081 и проверяет, что всё поднялось. Работает от того же
пользователя, что и релей, — иначе служба не прочитает собственный каталог.

Адрес клиентам прописывать НЕ НУЖНО: сервис ставится на тот же VPS, что и
база, поэтому по умолчанию и ПК, и телефон берут хост базы и порт 8081.
Переопределить (или выключить) можно строкой в `ip.txt` — там же, где база,
сигналинг и сервер звонков:

```
files=http://5.181.23.167:8081   # другой адрес или порт
files=-                          # выключить: вложения снова идут в базу
```

На телефоне то же поле есть в «Настройках». Сервиса нет или он не отвечает —
клиенты сами возвращаются к старому пути через базу: ничего не ломается, но
крупные файлы снова едут медленно.

Колонки `file_url`/`file_size` приносит миграция 26 (`sql/2026-10-13_file_url.sql`
или `sql/pismo-all.sql`). Без неё клиенты тоже работают по-старому.

## Доступ

Загрузка требует `Authorization: Bearer <jwt>`, подписанный тем же
секретом HS256, что у релея (`JWT_SECRET`): клиенты такой токен уже умеют
выписывать. Скачивание — по ссылке без токена: ссылка и есть отпечаток
содержимого, подобрать её нельзя.

`REQUIRE_JWT=0` снимает проверку — только для отладки.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `FILES_PORT` | 8081 | порт |
| `FILES_DIR` | `/opt/pismo-ws/files` | где хранятся файлы |
| `FILES_MAX_SIZE` | 2 ГБ | потолок на файл |
| `JWT_SECRET` | как у релея | подпись токена |
| `REQUIRE_JWT` | 1 | проверять токен |

## Обслуживание

* Логи: `journalctl -u pismo-files -f`
* Хранилище: `FILES_DIR/blobs` — имена файлов это их sha256.
* Недокачанное лежит в `FILES_DIR/tmp` и само убирается через сутки.
* Бэкап: каталог `blobs` — обычные файлы, им не нужен дамп базы.
